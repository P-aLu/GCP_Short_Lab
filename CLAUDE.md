# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Goal

This repository is a **full infrastructure-as-code, iterable Google Cloud training lab**. The intent is that any learner can clone this repo, run a single command, and get a fully provisioned GCP environment to practice against — then tear it down just as easily. Labs must be modular, repeatable, and cost-conscious.

## Repository Layout (intended)

```
.
├── CLAUDE.md
├── docs/                    # Architecture, conventions, per-lab notes
├── modules/                 # Reusable Terraform modules (one folder per concern)
│   ├── network/
│   ├── compute/
│   ├── iam/
│   └── ...
├── labs/                    # Lab definitions — each is a standalone Terraform root
│   ├── lab-01-gsc-privesc/  # GCP privilege escalation via stolen SA key + tfstate
│   └── ...
├── scripts/
│   ├── lab.sh               # Deploy / destroy a single lab
│   └── all-labs.sh          # Deploy / destroy every lab in order
└── terraform.tfvars.example # Template — never commit real .tfvars
```

Each `labs/lab-XX-*/` directory is a **self-contained Terraform root module** that calls modules from `modules/`. Labs must be deployable independently.

## Common Commands

### Auth & project setup
```bash
gcloud auth application-default login
gcloud config set project <PROJECT_ID>
```

### Deploy a single lab
```bash
./scripts/lab.sh apply   lab-01-gsc-privesc
./scripts/lab.sh destroy lab-01-gsc-privesc
```

### Deploy all labs at once
```bash
./scripts/all-labs.sh apply
./scripts/all-labs.sh destroy
```

See [`docs/deployment.md`](docs/deployment.md) for prerequisites, state-bucket setup, skip flags, and troubleshooting.

### Lint & format
```bash
terraform fmt -recursive          # format entire repo
tflint --recursive                # lint all modules and labs
```

### Generate module docs
```bash
terraform-docs markdown . > README.md   # run inside a module directory
```

### Run pre-commit hooks manually
```bash
pre-commit run --all-files
```

## Documentation Maintenance

Every task that changes code, infrastructure, or structure must also update the relevant docs **in the same response**. Never leave docs stale.

| What changed | Docs to update |
|---|---|
| New lab added or renamed | `docs/labs/README.md` (tracker table), `README.md` (lab catalogue) |
| Lab stage started or modified | `docs/labs/README.md` (kill-chain checklist, status column) |
| New module created | Module's own `README.md` (via `terraform-docs`), `docs/architecture.md` |
| Deployment behaviour changed (scripts, backend, vars) | `docs/deployment.md`, `README.md` quickstart if commands changed |
| New tool or toolchain requirement | `README.md` requirements table, `CLAUDE.md` toolchain table |
| Repo layout changed (new dir, renamed path) | `README.md` layout tree, `CLAUDE.md` layout tree |

**Rule:** if a doc file listed in the Supplementary Docs table is affected by a task but does not exist yet, create it — do not skip the update.

## IaC Conventions

- **Every lab** must have: `main.tf`, `variables.tf`, `outputs.tf`, `README.md`.
- **Every module** must expose a `README.md` generated by `terraform-docs`.
- Variable names use `snake_case`. Resource names use hyphens in GCP labels, underscores in Terraform identifiers.
- All resources must carry at minimum these labels: `env`, `lab`, `owner`.
- Use `lifecycle { prevent_destroy = false }` explicitly in lab roots so teardown is never blocked.
- Locals block at the top of `main.tf` for computed names/tags — no string interpolation scattered through resource blocks.
- Remote state: use a GCS backend per lab (`backend "gcs" {}`). The bucket name is a required input variable, never hardcoded.

---

## Cost Controls

- Default machine types: `e2-micro` or `e2-small` unless the lab explicitly requires more.
- Disks: standard persistent (`pd-standard`) unless the lab teaches disk types.
- Always wire up `terraform destroy` as the cleanup step in lab instructions.
- See `docs/cost-controls.md` for per-service guidance.

## Lab Tracker

**Canonical source of truth:** [`docs/labs/README.md`](docs/labs/README.md)

That file tracks every lab with a three-state status:
- `[ ]` not started
- `[~]` in progress / under construction — Claude may set this
- `[x]` done — **only the repo owner may set this**

Always update `docs/labs/README.md` when starting, modifying, or completing a lab or any stage within one. Never mark a step `[x]` autonomously.

---

## Lab Types

Labs may be **infrastructure labs** (learner builds something) or **security/CTF labs** (learner attacks a pre-deployed environment).

Security labs deploy a vulnerable-by-design environment. The `README.md` for each security lab describes the attacker's starting position and the intended kill chain.

## Adding a New Lab

1. Copy `labs/lab-00-template/` → `labs/lab-XX-short-name/`
2. Update `variables.tf` with any lab-specific inputs.
3. Write the scenario in `README.md` (what the learner will build and why).
4. Add an entry to `docs/labs/README.md`.
5. Run `terraform validate` and `tflint` before committing.
